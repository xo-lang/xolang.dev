Agents write the code. The compiler reviews every line.

Xo (pronounced ex-oh, like the letters X and O) is a fast, statically typed language for backends, tools, and web services. Every check reports JSON with stable codes and ready-made fixes, so an agent can write, check, and repair a service quickly and properly.

// why xo

Ideas from great languages, in one small one.

Xo borrows what has proven itself in Go, Rust, Swift, and Kotlin, and turns the bugs tests usually miss into compile errors. In a study of 30 planted safety bugs, Xo caught or prevented 23 to 29, against 13 for Go with strict analyzers and 9 for plain Go.

from Go

Small and fast

Few keywords, one obvious way, one formatter, fast builds, and static binaries for linux, darwin, windows, and wasi.

from Rust

Errors you can't ignore

Result and ?; an unhandled error is a compile error.

from Rust and ML

Sum types, exhaustive match

Every case handled, and every match target.os arm type checked for every target.

from Swift and Kotlin

No nil

Optionals are T? and checked at every use.

from Swift and Kotlin

Structured concurrency

No task outlives its scope; value semantics mean no data races.

// supply chain

A dependency can only do what you let it.

Put a ceiling on a dependency in xo.mod. If an upgrade starts doing more, the build fails at your call, before the new code ever runs. No mainstream language checks limits per dependency in the compiler: Go and Rust rely on audits and analysis tools (Capslock, cargo-vet), Deno and Node grant permissions per process rather than per dependency, and Java's SecurityManager is disabled as of JDK 24. The closest peers are a research language (Flix) and run-time systems (WASI components, LavaMoat).

an upgrade that reaches into Go
$ cat xo.mod
module example.com/shop

require github.com/acme/billing v1.4.1 uses none
$ xo check .
main/main.xo:4:6: error XO1309: `charge` of github.com/acme/billing v1.4.1
  performs `go`, above the effect ceiling `uses none` of that dependency in xo.mod

  note: review why github.com/acme/billing needs `go`; then raise the ceiling,
  or require a version within it (decision 0086)
enforced today

Authority is handed over

A library cannot open the network, files, clock, environment, or processes unless it is handed a capability value, and every one starts at main(os: Os).

enforced today

Effects in every signature

Every pub function declares what it does (uses net, fs.read), and the compiler checks the body against it, so a library's Xo code cannot misstate it.

enforced today

A ceiling per dependency

require ... uses none bounds what a dependency may declare. An upgrade that adds a call above it fails the build at the call site (XO1309).

enforced today

Escape hatches are labeled

Every call into Go performs the effect go, which cannot be declared away. A dependency's C bindings count only when your own module vouches for them (XO1316).

enforced today

Effects are locked

xo.lock records each dependency's effects. An update that adds one fails until you approve it (XO1317), and xo publish rejects a minor or patch release that adds one (XO1310).

enforced today

Capabilities you can narrow

os.net.only(["api.example.com"]) hands a library a network that reaches only those hosts; Env.only and Proc.only do the same for variables and commands. Checked at run time, on the Go backend today.

enforced today

Logging is an effect

Writing a log record is the log effect, so a ceiling can forbid it and an update that starts logging shows up like any other.

enforced today

xo audit

One report of every dependency's effects and escape hatches (go, C, log).

enforced today

Nothing runs at install

No build scripts and no install hooks, a common attack path elsewhere (npm postinstall, Rust build.rs). xo.lock and a checksum log pin every module.

Measured. We rebuilt 15 attack scenarios from the Backstabber's Knife Collection taxonomy (Ohm et al., 2020) as small malicious Xo dependencies, and Xo blocks 10 of them: 1 at fetch, 7 at xo check, 1 by the effect lock, and 1 at run time. Four are blocked by default (an install hook, code that runs on import, an unvouched C binding, and a malicious update); the other six are blocked once the app sets a ceiling or narrows a capability. The five not blocked: a wrong result and a runaway loop perform no effect, so no effect system can see them; sending data over the network or through logs, when the app grants both and sets no ceiling (it still shows in signatures, xo.lock, and xo audit); and a C binding that lies after the app vouched for it, since Xo cannot see inside C.

Limits today. Ceilings and narrowed capabilities are opt-in: without them, a dependency you hand os.net can use it, in plain sight. Narrowed capabilities work on the Go backend; the native backends are planned. A vouch for C is your own review. This is checking at compile time plus capabilities at run time, not a process sandbox; tests and contracts remain the defense against wrong answers.

The plan, in order

One stage in flight at a time. Most stages move the compiler into Xo, each checked against the Go implementation until the output is identical; the Go implementation stays the reference for the Go and LLVM backends. The order is set; there are no dates.

  1. ✓

    Front end in Xo

    The lexer, parser, and type checker give output identical to the Go compiler on all three backends: 610 of 626 repository programs (the other 16 call Go or C).

  2. ✓

    SSA builder in Xo

    All 8 stages. 11,708 of 11,734 functions identical to the Go builder's SSA (it rejects the other 26 too), and 6,282 of 6,376 in test binaries (the rest fail there too). The passes give identical output on all 307 programs that fully build and 45 test binaries, and the verifier agrees on 32,450 mutated programs. No differences on any backend. Built with LLVM, a full run through every pass and the verifier takes 1.05x the time of the Go-built compiler (1.3x with the Go or arm64 backend); the build step alone, 1.6x to 2.3x.

  3. ✓

    Supply-chain safety by default

    Only your own module vouches for a dependency's C bindings, xo.lock locks each dependency's effects, capabilities can be narrowed at run time, xo audit reports it all, and logging is an effect. Against 15 attack scenarios from the Backstabber's Knife Collection: 10 blocked.

  4. ●

    Prebuilt runtime

    In progress. Releases ship the native C runtime prebuilt for each target, so arm64 builds need no clang. Today they still need it once, to compile that runtime. The LLVM backend keeps using clang to compile its LLVM IR.

  5. ○

    arm64 emitter in Xo, then the switch-over

    When the Xo compiler builds itself to a byte identical fixed point and passes the arm64 tests, the released xo on arm64 hosts becomes the self-hosted compiler for native builds.

  6. ○

    Runtime pilot

    Port one small file of the C runtime to Xo and compare output and speed, to decide whether the runtime moves to Xo, as Go's did.

  7. ○

    Standard library for tools

    Command line parsing, running other programs, terminals, files, formats, shell completions, and version stamping, each designed in a recorded decision first.

  8. ○

    WebAssembly backend

    SSA to .wasm, written in Xo, so the playground runs the Xo compiler itself, with no Go compiler or linker to download.

  9. ○

    LLVM emitter in Xo

    The LLVM backend's code generation moves to Xo.

  10. ○

    Go code generator in Xo

    Last, since only the Go backend needs it. That backend keeps using the Go toolchain for your programs, use go, and Go's targets.

How Xo builds

Every Xo program compiles to Go. The compiler checks your code, writes Go source that points back to your .xo lines, and the Go toolchain builds it, so Go's garbage collector, scheduler, cross compilation, and debugger come for free, and stack traces name Xo lines. The Go backend builds the whole language and is the reference the others are tested against. The native backends are a second way to build the same program, for when you want no garbage collector. Interop differs by backend: native builds can call C with use c, and the Go backend can call any Go package with use go (C stays off the Go backend so its binaries stay static and cross compile anywhere).

reference · default

Go backend

Builds every program that does not call C, on every target, and can use go any Go package.

xo build
native · preview

LLVM backend

Lowers Xo's own SSA form to LLVM IR and builds optimized native code with clang.

xo build --no-gc --backend=llvm
native · preview

arm64 backend

Writes AArch64 assembly straight from the same SSA form, with no LLVM in the way, for fast builds on arm64 Macs and Linux.

xo build --no-gc --backend=arm64
native

No garbage collector

With --no-gc, memory is freed by reference counting the moment its last owner lets go, and a value with one owner is updated in place. What a native build cannot handle yet is a compile error (XO1201) naming it, never a surprise at run time.

native

Real time

Mark a function uses realtime and the compiler requires bounded loops, no recursion, and no allocation in it; frees that would land in it wait until it returns. For control loops and audio.

all three

Same answers

The test programs run on all three backends and must print the same output, so a native build behaves like the Go build it is checked against.
